The historical review/evidence below is not retroactively upgraded, and protocol trust/order and public-loader deferral remain applicable.

M4 is an earned-composition investigation, not a requirement to ship descriptors. **Retain the existing plain render functions and shared trusted snippets; do not extract another semantic module layer now.** No source, public API, emitted protocol, storage format, schema, runtime hook or lifecycle change is proposed. [BACKLOG](../BACKLOG.md#12-ordered-implementation-backlog) alone owns subsequent work; M5 and gated quality evidence are not approved by this decision.

## Actual composition and rule ownership

- **Policy selection:** `lib/extension.ts` contributes the owned section at `before_agent_start`, then `context_with_system` checks physical/original context eligibility and accepted preparation and refreshes Active/bootstrap, available Passive, or no section for Off. These are two lifecycle delivery calls to the same producer, not two separately authored protocols. Validated captured WANTED scopes and bootstrap policy are the renderer inputs, not semantic memory values.
- **Trusted text:** `lib/protocol.ts` owns `stateFlowProtocol(bootstrap, scopes)` and `passiveMemoryProtocol(scopes)`. Scope selection is captured against the closed owner set before interpolation. It is DATA, not an acquisition or publication capability. No arbitrary state content, file body or user-supplied module callback is an input to these renderers.
- **Existing shared snippets:** `TASK_DRIVEN_HISTORY`, `PATCH_RESULT_PROTOCOL` and `FLAT_INTERFACE_PROTOCOL` each already serve Active and Passive consumers. `RESPONSE_PATCH_GUIDELINE` is reused by Passive and actual tool prompt guidelines; both native read/patch declarations also use `SCOPE_PARTICIPATION_GUIDELINE`. `scopeGuidance` shares selected-owner meaning/non-broadening rules. These are deliberate existing extractions, not a newly proposed framework.
- **Semantic plane summaries:** Intents/Strategy/Tactics have one summary site in Active's STATE block. Bootstrap prepends a conditional notice to the same Active renderer, not a copied second three-plane protocol. Passive deliberately does not inherit Active iteration/reconciliation pressure. The larger MEMORY/REFS paragraphs express cross-plane preservation and ownership obligations, not three independently enableable features.
- **Section membrane:** `lib/context.ts:projectSystemProtocol` replaces/removes only the owned `state_flow` section, preserves foreign sections/system frames and reuses an unchanged projection. It does not invent system authority when no native system frame exists. It accepts the trusted caller's text; it does not generate instructions from `ContextView.state`.
- **Fallible state and output:** Context heads/notices/continuation state are user-level DATA owned by `context`, with policy/data translation by `model-interface`; they do not become instruction fragments or get publication authority from a projection ID.
- **Enforced semantics:** Same-scope intent cascade, recursive patching, artifact/Skill placement and source provenance stay in `ownership`/`transition`/source owners. Causal replay/private/current publication stay in temporal/runtime/storage owners. A prompt fragment is not an `afterPatch` hook or a second engine.
- **Diagnostics:** Existing diagnostic formatting in `protocol` and persistence in `logging` have named consumers/contracts. Splitting files merely to shorten the protocol file is not the M4 outcome. Error owner names preserve provenance and must not be flattened into local permission.

Overlap between STATE summaries, detailed MEMORY/REFS guidance, tool guidelines and packaged Skill examples is not automatically producer duplication. They teach different scopes/authorities/detail levels. This inspection does not claim all natural language is perfect or all models interpret it consistently. It finds no executable mode/scope/trust conflict requiring a new composition mechanism.

## Alternatives evaluated

### A — Retain functions and current snippets (selected)

Keeps a local, fixed-order trusted template with mode/scope/bootstrap distinctions visible together. Shared obligations with multiple consumers already have narrow names. Before/after retained production graph, emitted bytes, public surface and lifecycle dependencies are identical. The cost is continued local editing of the Active template and careful preservation of conditional wording. That is currently the simpler honest cost, not a demonstrated defect.

### B — Additional private plain helpers or plane strings

A small helper is appropriate when a second real trusted producer must share a rule. Today moving the three summary lines into an extra function/constant serves one Active site; bootstrap already reuses that site. Generalizing response/scope wording risks obscuring real differences: selected legacy response versus new Session-only answers, one-owner transfer refusal versus genuine multi-owner moves, and Passive access versus Active reconciliation. No second consumer or conflicting edit was found to repay another name/parameter boundary.

The strongest real local duplication is the three owner meanings: `scopeGuidance`'s map and the compact inline all-three Active sentence both author them. They currently agree. Subset wording adds exclusion/participation obligations and ordering, while the default body is deliberately compact and hash-guarded. One private meaning helper could preserve exact bytes; no current bug or conflicting update requires it. A bug is not a prerequisite for preventive deduplication: a future authorized owner-meaning change may reasonably use that helper before drift occurs. Current retention weighs the small local synchronization cost against another boundary; it does not forbid that choice. This is real consistent duplication, not a claim of zero repeated text.

This is not a prohibition on future small helpers. It rejects extraction solely for symmetry or file length. Exact output preservation would not itself reduce prompt bytes; wording changes are a separate semantic claim.

### C — Static internal descriptors and fragment assembly

A private ordered descriptor array could hold text or policy-only renderers without a public registry. In this code it adds fragment keys, assembly/dispatch and output-order obligations while carrying the same text. Three plane descriptions alone do not require per-plane enablement, versioning or execution. Moving MEMORY/REFS/source/lifecycle rules into plane callbacks would cross existing ownership boundaries rather than simplify them.

No runnable descriptor prototype was created: no unresolved dependency or behavior question requires one after inspecting the current single producer and existing shared fragments. Equal text would mean equal output by construction, not an independently measured prototype result or cognitive improvement. A loader, declarative public manifest, external registration, optional-module UI, executable invariant or hidden reaction is outside this M4 choice; M5 separately owns any demonstrated demand.

## M4 acceptance disposition

- **M4.1:** The source-level rule/producer map and three alternatives support no further extraction now. Existing private shared fragments remain, rather than pretending M3 left an entirely uncomposed monolith.
- **M4.2:** There is no candidate graph to integrate. Preserve the existing trusted mode/section composition and its accepted protocol/context/native witnesses unchanged; no before/after source rewrite, parser, storage or lifecycle dependency is introduced.
- **M4.3:** No maintainability or cognitive benefit of an additional descriptor layer was demonstrated. Retain the simpler implementation and defer the refactor, not declare a positive/negative live-model result. The permitted neutral decision is not completion of an unrun cognitive experiment. Any later model-quality/retention/retry/cost assertion still belongs to explicitly gated M0.4b evidence.

## Conditions for revisiting the decision

Revisit for an authorized owner-meaning change where preventive single-source editing repays its cost, a concrete second trusted consumer with demonstrated rule duplication, a reproducible contradictory-mode edit that a smaller boundary prevents, or an accepted independently selectable internal protocol requirement with a clear fixed-order/trust contract. A proposed rewrite must preserve actual obligations and foreign/forced section precedence and show a concrete maintainability gain; behavioral/cognitive claims need their own authorized evaluation. These are falsification conditions, not tasks or a license for a registry/API. Canonical remaining work stays in BACKLOG.
